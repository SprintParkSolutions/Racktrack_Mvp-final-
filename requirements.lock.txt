# requirements.lock.txt — pinned, reproducible Python dependency set.
#
# TARGET RUNTIME: Linux + CPython 3.11 (the Dockerfile's python:3.11-slim, and
# the Windows GPU box's Python 3.11). All pins below were chosen for that target.
#
# HOW THIS WAS PRODUCED (2026-07-22)
#   The previous version of this file was reconstructed by reading package
#   metadata out of a *Windows* .venv (a GUI/CV working env), not from a clean
#   `pip install && pip freeze` on the runtime image. That produced three
#   defects, all fixed here:
#     1. numpy was pinned to 2.4.6, which VIOLATES the `numpy>=1.26,<2.0`
#        constraint in requirements.txt (an internal contradiction).
#     2. five direct dependencies were missing exact pins (easyocr, openpyxl,
#        msal, psycopg2-binary, python-dotenv) — listed only at their floor.
#     3. the transitive block was resolved against a numpy-2.x / newer-torch
#        Windows env, so it does NOT match the numpy-1.x generation pinned here;
#        those stale transitive pins have been removed (see "TRANSITIVES" below).
#
# NUMPY CONTRADICTION — RESOLVED IN FAVOUR OF numpy<2.0 (numpy==1.26.4):
#   The `numpy>=1.26,<2.0` ceiling in requirements.txt WINS; this lock conforms
#   to it rather than silently overriding the app's stated constraint. Reasons:
#     * numpy 2.0 broke the C ABI: any extension compiled against numpy 1.x
#       aborts at import under numpy 2.x. Pinning the whole numpy-1.x generation
#       removes that runtime hazard outright.
#     * easyocr 1.7.2 (the stack's laggard) and several compiled transitives are
#       only reliably exercised on numpy 1.x.
#     * the packages pinned below form a numpy-1.x-consistent set, verified from
#       PyPI metadata: torchvision 0.19.1 requires torch==2.4.1; ultralytics
#       core requires numpy>=1.23.0 (and pins numpy<2 on darwin); opencv 4.10 on
#       py3.11 requires numpy>=1.23.5. numpy 1.26.4 satisfies all of them.
#   numpy 1.26.4 is the final 1.26.x release — a stable, reproducible floor.
#
# DEPENDENCY-CONFUSION FLAG (not changed here — flagged for review):
#   The Dockerfile and CI install torch/torchvision with
#       --extra-index-url https://download.pytorch.org/whl/cpu
#   An *extra* index means pip considers BOTH that host AND public PyPI and
#   picks the highest version, so a malicious public-PyPI upload of a torch
#   build number higher than the CPU-wheel index could be preferred — the
#   classic dependency-confusion shape. Prefer `--index-url` (single, trusted
#   source) over `--extra-index-url`, or pin exact versions/hashes. Left as-is
#   because the Dockerfile/CI are owned elsewhere; call it out in review.
#
# GPU/CUDA NOTE (Windows box): plain `pip install torch==2.4.1` from PyPI yields
#   the CPU build on Windows. If CUDA is required, install torch/torchvision
#   from the appropriate PyTorch CUDA index — do NOT rely on this bare lock for
#   a GPU build.
#
# USAGE (reproducible install on the runtime image):
#   pip install -r requirements.lock.txt
#
# TRANSITIVES: this file pins the 13 DIRECT dependencies exactly. To produce a
#   fully transitive-pinned lock, run on a clean TARGET (Linux/CPython 3.11)
#   image:  pip install -r requirements.lock.txt && pip freeze > requirements.lock.txt
#   The stale Windows-venv transitive pins were removed deliberately: pinning
#   them alongside numpy 1.26.4 would reintroduce conflicts, since they were
#   resolved against numpy 2.x.
